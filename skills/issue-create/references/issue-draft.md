# 이슈 초안 작성

초안의 목표는 하나다. **`issue-start` 가 읽고 바로 분석에 들어갈 수 있을 것.**
`issue-start` 는 본문에서 재현 조건, 기대와 실제, 환경, 완료 기준을 뽑아 쓴다. 그 자리를 미리 채워 둔다.

요청이 여러 항목으로 분해됐으면 **항목마다** 아래 틀을 따로 채운다. 분해 판정은 [`split-requests.md`](./split-requests.md).

## 저장소 템플릿 우선

```bash
ls .github/ISSUE_TEMPLATE/ 2>/dev/null
cat .github/ISSUE_TEMPLATE/*.md 2>/dev/null | head -60
```

템플릿이 있으면 그 항목 구성을 그대로 따른다. 아래 기본 틀은 템플릿이 없을 때만 쓴다.

## 기본 틀

```markdown
## 배경

<왜 이 변경이 필요한지 2~3줄. 사용자 요청 원문의 의도를 보존한다>

## 요구사항

- <바뀌어야 하는 것 1>
- <바뀌어야 하는 것 2>

## 현재 동작 / 기대 동작

- 현재: <지금 이렇게 된다>
- 기대: <이렇게 되어야 한다>

## 재현 조건 (수정 이슈일 때)

- 경로: <URL 또는 화면>
- 입력값/상태: <로그인 여부, 선택 상태, 데이터 조건>
- 환경: <브라우저 폭, 다크모드, 언어, 런타임 버전>

## 완료 기준

- [ ] <검증 가능한 조건 1>
- [ ] <검증 가능한 조건 2>

## 영향 범위 (추정)

- `<파일 또는 계층>` — <왜 여기가 걸리는지>

## 선행 이슈

- [ ] [#<번호>](<이슈 URL>) <제목>

## 후행 이슈

- [ ] [#<번호>](<이슈 URL>) <제목>

## 참고

<스크린샷·로그·링크 자리. 없으면 "없음">
```

## 선행 · 후행 이슈

이슈 사이의 작업 순서를 본문에 남긴다. 완료 기준처럼 **체크박스**로 적어, 본문만 보고 연결된 이슈가 끝났는지 확인할 수 있게 한다.

```text
선행 이슈   이 이슈보다 먼저 끝나야 하는 이슈
후행 이슈   이 이슈가 끝나야 진행할 수 있는 이슈
[ ]         아직 안 끝남
[x]         해당 이슈가 닫힘 (merge 완료)
```

- **항목마다 이슈 링크를 반드시 남긴다.** `- [ ] [#12](https://github.com/<owner>/<repo>/issues/12) <제목>` 형식으로 쓴다.
  `#12` 처럼 번호만 쓰지 않는다. 링크가 있어야 어느 트래커에서든 바로 이동해 진행 상태를 확인할 수 있다.
- 주소는 직접 조립하지 않고 `gh issue view <번호> --json url,title` 로 받아 쓴다.
- 연결은 양쪽에 남긴다. 이 이슈의 선행에 #12 를 적으면 #12 의 후행에도 이 이슈를 적는다.
- 연결된 이슈가 닫히면 상대 본문의 해당 항목을 `[x]` 로 바꾼다. 이 버전에는 자동 기록·체크가 없으므로 작성자가 손으로 갱신한다.
- 연결이 없으면 섹션을 지우지 말고 항목 대신 `없음` 으로 둔다.

```markdown
## 선행 이슈

- [x] [#9](https://github.com/<owner>/<repo>/issues/9) 주문 목록 API 페이지네이션
- [ ] [#12](https://github.com/<owner>/<repo>/issues/12) 대시보드 기간 필터 추가

## 후행 이슈

- [ ] [#15](https://github.com/<owner>/<repo>/issues/15) 대시보드 카드 정렬 고정
```

## 성격별 추가 항목

```text
frontend   화면 경로, 뷰포트, 스크린샷 자리, 관련 컴포넌트 추정
backend    엔드포인트, 요청/응답 예시, 현재 지연·에러율, 데이터 정합성 조건
both       위 두 묶음을 계층별로 나눠 적는다
```

`issue-end` 가 증거를 만들 때 이 항목을 그대로 쓴다. frontend 면 캡처 조건, backend 면 측정 대상이 된다.

## 제목

- 핵심 명사구로 짧게. `issue-start` 가 영문 kebab-case slug 를 만들기 쉬운 형태가 좋다.
- 좋은 예: `탭 활성 상태가 새로고침 후 초기화됨`, `주문 목록 API 응답 지연`
- 나쁜 예: `버그 수정해주세요`, `개선 요청`
- 형제 이슈끼리는 제목만 보고 구별되게 **범위를 제목에 담는다**. `대시보드 개선` 셋보다 `대시보드 기간 필터 추가` / `대시보드 카드 정렬 고정` 이 낫다.

## 원본 요청 기록

`create --request-file` 로 넘길 파일에는 **원본 요청 전문 + 이 이슈가 맡는 범위 +
fan-out/fan-in 관계 근거** 를 함께 담는다.
분해된 이슈는 서로의 번호를 모르므로, 이 파일이 `issue-start` 4단계 대조 분석의 유일한 맥락이다.

```markdown
## 이 이슈 범위와 관계 근거

범위: 대시보드 기간 필터 추가만. 목록 빈 렌더링과 export 스크립트 제거는 별도 이슈.

관계 근거: fan-out. 세 작업은 각각 별도 배포·검증·취소·되돌리기가 가능하다.

## 원본 요청

> 대시보드에 기간 필터 넣고, 주문 목록이 가끔 비는 것도 고치고,
> 안 쓰는 export 스크립트도 지워줘
```

항목이 하나뿐이면 `--request-file` 을 생략한다. `--body-file` 이 그대로 기록된다.

## 라벨

저장소에 **실제로 있는 라벨만** 붙인다.

```bash
node <skill>/scripts/issue-create.mjs labels
```

매핑은 `issue-start` 의 브랜치 prefix 추론과 맞춘다.

```text
수정 요청      bug          → issue-start 가 fix/ 로 분기
추가 요청      enhancement  → feat/
문서           documentation → docs/
삭제·정리      chore        → chore/
```

쓸 라벨이 저장소에 하나도 없으면 `label-audit.md` 의 절차대로 **승인을 받고** 만든다. 승인 없이 만들지 않는다.
등록 후 기존 이슈의 라벨 점검까지가 한 세트다. 세부는 `label-audit.md`.

### 대상 버전 라벨

버전 관리를 하는 저장소면 초안의 라벨 줄에 대상 버전 라벨을 함께 적는다.

```bash
node <skill>/scripts/issue-create.mjs version-label
```

`VERSIONED=0` 이면 버전 라벨 없이 진행한다. 아니면 `VERSION_LABEL`(패치 +1)을 기본으로 쓴다. **패치는 묻지 않는다.**

변경이 크다고 판단될 때만 마이너 올림을 제안한다. 아래 중 하나라도 해당하면 큰 변경이다.

```text
새 기능 단위      새 스킬·명령·화면·API 처럼 사용자가 새로 쓰게 되는 것이 생긴다
쓰는 법이 바뀜    기존 명령·옵션·설정·출력의 동작이 바뀌어 사용자가 방식을 바꿔야 한다
범위가 넓음       여러 계층·여러 스킬에 걸친 개편이거나, 한 요청이 여러 이슈로 분할됐다
사용자의 표현     "큰 업데이트", "개편", "대규모" 처럼 규모를 직접 말했다
```

버그 수정·문서·정리(`bug` / `documentation` / `chore`)는 범위가 넓어도 패치로 둔다.

큰 변경이면 초안 승인 AskUserQuestion 에 질문을 하나 더 넣어 함께 받는다. 여러 건이면 묶음 전체에 한 번만 묻는다.

```text
질문   변경 규모가 커 보입니다. 대상 버전을 무엇으로 할까요?
- 마이너 version:0.4.0 (권장)   MINOR_LABEL. create 에 --bump minor 를 넘긴다
- 패치 version:0.3.9            VERSION_LABEL. 기본값 그대로 등록한다
```

**메이저는 선택지에 넣지 않는다.** 사용자가 요청에서 메이저 버전을 명시했을 때만 `--bump major` 를 쓰고, 그때는 묻지 않는다.
사용자가 특정 버전을 직접 지정했으면(`version:0.5.0` 으로 달아줘) 그 값을 `--label` 로 넘긴다.

## 승인

초안 전문을 그대로 보여주고 AskUserQuestion 으로 받는다. 여러 건이면 **전부 한 번에** 보여주고 한 번에 받는다.

```text
등록          이대로 등록 (여러 건이면 전부)
등록 없이 진행 이슈를 만들지 않고 스킬을 빠져 원래 변경 요청을 그대로 진행
수정          어느 이슈의 어느 항목을 고칠지 받아 그것만 다시 초안 제시
취소          등록하지 않고 원래 요청도 진행하지 않은 채 종료
```

`등록 없이 진행` 은 이번 한 번만 `issue.createMode=direct` 처럼 동작한다. 설정 파일은 바꾸지 않고, `.issue/<번호>/request.md` 도 남기지 않으며, 7단계 라벨 점검과 8단계 4지선다도 건너뛴다.

분할안은 2단계 이전에 이미 승인받았다. 여기서 이슈 개수를 다시 흥정하지 않는다.
